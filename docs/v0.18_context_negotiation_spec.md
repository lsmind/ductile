# v0.18 上下文协商规格（declare-then-run）

状态：提案（用户定调 2026-09-11）。实现排在 v0.17.4 验证 ship 之后。

## 1. 动机与定位

v0.17 auto-prompt 是纯"推"模型：引擎按八段模板一次性合成上下文，模型被动接受。
盲评实证两处输分（s3 -7.3 审计缺清单、s1 -15 约束被截断）都是**注入不足**——
引擎猜错了模型需要什么。v0.17.3 `.needs()` 与 v0.17.4 约束敏感窗口是修补；
本规格把 guessing 换成 asking：**模型声明缺什么，引擎补什么，再重启模型**。

### 为什么不是工具循环（用户裁定）

- **不要 loop 工具调用**：模型不持句柄、不开会话、不执行命令。每轮 LLM 调用
  完全无状态，桥（llm_bridge.py 单发 CLI）无需改造。
- **循环在引擎不在模型**：预算控制、信息解析、失败分类全部在 Rust 侧，可单测、
  可复现、可进回归门禁。
- **声明而非拉取**：模型只能说"我缺 @req.constraints"，给不给、给多少由引擎
  按 preview_window 分级决定——窗口纪律不因协商而旁路。

## 2. 协商协议

### 2.1 输出契约扩展

协商开启的节点，输出契约二选一（模型自判）：

```json
// 信息不足——声明缺口，本轮不产出结果
{"enough": false,
 "missing": [{"ref": "@req.constraints", "why": "选型需要预算与复杂度边界"}]}

// 信息充足——正常产出（enough 字段可省，省略 = true）
{"enough": true, "modules": [...], "storage": "...", ...}
```

规则：
- `enough=false` 时**不得**输出业务字段；`enough=true`（或省略）时必须带全
  schema 字段——违者走 errflow format/schema 分类（Reroute）。
- `missing` 每条必须带 `ref`（可解析引用）+ `why`（一句话用途）。`why` 缺失
  或 ref 不可解析 → 引擎回"unavailable"，不重试同一条（防死循环讨要）。

### 2.2 引擎侧补料（resolve）

missing.ref 解析表（按序尝试）：

| ref 形态 | 解析 | 窗口 |
|---|---|---|
| `@proc.field` | 上游结构化字段值 | preview_window（消费方 schema 分级） |
| `@proc` | 上游完整文本 | 全文（模型显式点名要） |
| `topic` | 主题输入全文 | 全文 |
| `script:<name>` | scripts 表契约卡 | 契约卡即全文 |
| `hyper:<query>` | 相似节点/管线列表 | 名单+desc |

解析失败（不存在的 proc/field/script）→ 补充块中回
`unavailable: @x.y（原因）`——模型得知不可得，下轮要么换 ref 要么带假设作答。

### 2.3 提示词积累（保留在节点）——核心语义

第 r 轮 prompt 定义（**追加，不重建**）：

```
prompt_0   = 八段合成（v0.17 现状）
prompt_r+1 = prompt_r + "\n\n# 补充信息（协商第 r 轮）\n" + 补充块
```

- **只增不减**：一旦信息进了 prompt，后续轮次永远在场——模型不会重复讨要
  同一条（重复要 → 引擎发现已在场 → 回 already-provided，且计一次浪费）。
- **协商历史持久化在节点执行记录**：runs 表新增 `negotiation` JSON 列，
  存 `[{round, prompt_len, missing, resolved, unavailable}]` 逐轮摘要 +
  最终 prompt 全文。`ductile stats` 可查——审计可回放"节点要了什么、
  引擎给了什么、第几轮认输/达标"。
- 最终产出结果的那一轮 prompt 即节点生效上下文，重放执行用同一份。

### 2.4 循环与预算（引擎侧）

```
round 0..N（N 默认 3，[agents.x] negotiate_rounds 可调，0=关闭协商）
  call(prompt_r)
  ├─ enough=true + 字段全 → 返回结果，协商日志落库
  ├─ enough=false + missing 非空 → resolve → 追加 → round r+1
  └─ 违约（enough=false 却带业务字段 / missing 空 / 重复讨要超限）
       → errflow format/data 分类，Reroute
预算耗尽仍 enough=false → fail-closed：Escalate + incident 记录
  （class=能力不足或描述错，交五分类归因闸）
```

### 2.5 开关与兼容

- 协商默认**关**（negotiate=false）：现有管线行为零变化，regchain 回归臂
  保持确定注入，regcheck3 门禁不受影响。
- `[agents.x] negotiate=true` 逐 agent 开启；`NEGOTIATE=0/1` env 全局覆盖。
- 新增独立回归探针 `negotiate_probe.pipeline`：断言①二轮收敛②重复讨要被拒
  ③预算耗尽 fail-closed ④协商日志落库。与 regchain 并列，不互相污染。

## 3. 与既有机制的关系

| 机制 | 分工 |
|---|---|
| `.needs(@ref)` | 静态声明：作者预知依赖，写进 DSL |
| preview_window 分级 | 静态窗口：引擎按消费方 schema 定视野 |
| 上下文协商（本规格） | 动态兜底：模型运行时发现缺口，引擎补 |
| cognition incidents | 事后回传：错了记下来，下轮前置注入 |

四者叠加的完整链：作者声明（needs）→ 引擎分级（window）→ 模型补要
（negotiate）→ 错误记忆（incident）。协商日志同时是 incident 归因的
证据源（"第 2 轮要过 @x 没给够"是 class2 上游投毒的直接证据）。

## 4. 验收标准

1. 单测：resolve 表全形态、追加不重建、重复讨要拒绝、预算耗尽 Escalate
2. negotiate_probe.pipeline 四断言全绿
3. regchain（协商关）跑分不退步
4. 真实场景冒烟：regconf architect 开协商，首轮 enough=false 要 constraints
   → 二轮收敛 → 产出贴约束（对比 v0.17.4 固定扩窗的产出）
