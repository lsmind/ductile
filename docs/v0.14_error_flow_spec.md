# v0.14 错误流规格 — 全自动错误处理（Either 内部值语义）

> 状态：实施中（a1 已合） · 2026-09-07 二次修订 · 两项用户裁定：
> ① 错误处理不单独配置，不能用 .eval——分类+策略统一收进 errflow.rs 模块内建；
> ② **不保留显式的 left/right**——错误流是引擎内部值语义，DSL 零新增语法

---

## 0. 问题（源码实证，executor.rs:116-310）

现状错误语义只有一层：`exec_proc` 全路径失败 → `Err(String)` → `exec_pipeline` 置 failed
直接 break。四大缺陷：

1. **错误是控制流不是数据**——无错误消费者机制（on_error/handler 全库 grep 零命中）
2. **部分结果全丢**——`ExecResult::Failed(String)` 不带已完成的 results，debug 素材清零
3. **错误不可分类**——timeout 和权限错误在引擎眼里是同一种东西（字符串）
4. **策略缺失**——权限错误被无谓重试、数据错误重复撞墙，所有失败一刀切 abort

## 1. 设计总纲

```
原始错误 ──→ errflow.rs 统一错误处理模块 ──→ executor 内部 Either 值语义
  stderr/io/exit/timeout    classify → ErrorRecord{code,…}       Left 落 results + 自动传播
                            strategy(code) → Retry/Reroute/Escalate    （全程无 DSL 面）
```

**全自动原则**：分类是引擎事实、策略是内置表、传播是隐式语义——用户不写任何
错误处理代码；`.pipeline` 语法零变更（v0.9 管线行为完全兼容，唯失败输出更丰富）。

## 2. 错误分类学（已实现，a1）

六类：`timeout` / `resource` / `permission` / `data` / `contract` / `crash`。
classify() 纯函数，模式库来自引擎全量错误串 + Python/bash stderr 常见形态；
判定顺序 contract → timeout → permission → resource → data → crash（先具体后兜底）。
`ErrorRecord` 编码复用 `§§FIELDS§§` 协议（err=1/err_code/err_proc/err_impl/err_msg/attempts + raw）。

## 3. 内置策略表（errflow.rs，硬编码不可配置）

```rust
pub fn strategy(code: ErrCode) -> Action {
    match code {
        ErrCode::Timeout    => Action::Retry { budget: 2, backoff: Backoff::Linear },
        ErrCode::Resource   => Action::Retry { budget: 1, backoff: Backoff::Linear },
        ErrCode::Permission => Action::Escalate,   // 权限重试无意义，直接上报
        ErrCode::Data       => Action::Reroute,     // 数据错→立即换 impl，不撞墙
        ErrCode::Contract   => Action::Escalate,   // 创作错误，fail-fast
        ErrCode::Crash      => Action::Escalate,   // 未知根因，不瞎猜
    }
}
```

| action | 行为 | 作用点 |
|--------|------|--------|
| `Retry{budget, backoff}` | proc 级重试预算：全 plan 失败后线性退避（1s,2s,…）整轮重跑（重排序自然降级已失败 impl） | exec_proc 外层 |
| `Reroute` | impl 传输层重试（`.retry(n)`）遇数据类错误立即放弃当前 impl、直切下一备选——同输入必再错，不浪费时间 | run_impl_with_retry |
| `Escalate` | 不自动处理：Left 落库 + 隐式传播 | — |

与 impl.retry 分工：`.retry(n)` 单 impl 传输层（指数退避，瞬时抖动）；errflow 策略 proc 级（可换 impl，线性退避），策略层在外。

## 4. Either 内部值语义（executor 变更）

**无 DSL 面**。用户管生管死，引擎管错误：

1. **错误值化**：策略耗尽仍失败 → `results[p] = Left(ErrorRecord.encode())`（§§FIELDS§§
   文本，`@p.err_code` 等字段现有机制天然可读）——失败从 abort 变成值
2. **隐式传播**：下游 proc 执行前检查上游引用（impl refs ∪ foreach source），任一为
   Left → 本 proc 不执行、直接落 Left（err_msg = `propagated from p`，err_code 继承）。
   隐性依赖不被静默跳过（fail-closed 传统）
3. **终局判定**：全部 proc 走完后，results 存在任何 Left → `ExecResult::Failed { error,
   partial }`（error = 首个原生 Left 的错误串；partial = 全部 results，含 Right 成果与
   Left 标记）；无 Left = Success（与今天一致）
4. **foreach**：单项失败语义不变（项级部分成功已有），全项失败走 proc 级 Left 路径
5. **e-graph 路径**：同语义（Left 插入 results 后继续，代表/别名照常 CSE——Left 值
   即结果值，等价类共享的是"失败"这一事实）

## 5. API 面（api.rs）

`run_json` 失败输出升级：

```json
{
  "ok": false,
  "error": "All paths failed for proc: render",
  "err_code": "timeout",
  "partial": { "search": "…", "render": {"err":1,"err_code":"timeout","err_msg":"…"},
               "report": {"err":1,"err_code":"timeout","err_msg":"propagated from render"} }
}
```

partial 中的 Left 值解码为干净对象（decode_internal_fields 同款）。

## 7. 边界与取舍

- **v0.9 兼容**：无新语法；唯一行为差异 = 失败时下游被标记传播（原先直接断流）+
  Failed 携带 partial（纯增量字段）
- **隐式传播默认开**：用户裁定不留显式控制——引擎比人可靠地记住"这个依赖死了"
- **策略表迭代** = 改 errflow.rs + 测试（枚举穷尽，无未知形态）
- **分类是启发式**：crash 兜底永不过时；模式库纯函数可迭代
- Saga 补偿（.undo 回卷）不在本期，真实场景驱动再议
