# v0.14 错误流规格 — Either 错误流 + 错误分类学 + 策略引擎

> 状态：实施中 · 2026-09-07 · 起因：用户裁定「异常处理太粗糙，应有 `<left, right>` 节点形成错误流策略；
> 对常见运行错误分类定策（源数据类型/数据处理/资源不可得/权限…），多层面识别分类，统一错误处理模块管理」

---

## 0. 问题（源码实证，executor.rs:116-310）

现状错误语义只有一层：`exec_proc` 全路径失败 → `Err(String)` → `exec_pipeline` 置 failed
直接 break。四大缺陷：

1. **错误是控制流不是数据**——`on_error/handler/compensat` 全库 grep 零命中，无错误消费者
2. **部分结果全丢**——`ExecResult::Failed(String)` 不带已完成的 results，debug 素材清零
3. **错误不可路由**——无法「渲染失败→走降级素材路径」这类错误分支
4. **错误不可分类**——timeout 和权限错误在引擎眼里是同一种东西（字符串），策略无从谈起

## 1. 设计总纲

```
             分類（errflow.rs）          策略（.eval）              流（.pipeline）
原始错误 ──→ ErrorRecord{code, …} ──→ on error.X 动作   ──→ Either: Left 错误流 / Right 成功流
  stderr/io/exit/timeout          retry/escalate/reroute    .when_err(@p) 错误路由
```

三权分立（沿用 v0.11 裁判分离传统）：

- **分类**是引擎事实（错误长什么样是客观的）→ `errflow.rs` 纯函数
- **策略**是运维关注点（timeout 该重试几次是人的决定）→ `.eval` 策略文件
- **流路由**是创作关注点（失败后走哪条路是流程设计）→ `.pipeline` 的 `.when_err`

## 2. 错误分类学（Taxonomy）

六类，覆盖引擎原生错误面 + 外部脚本 stderr 模式（`steps.rs`/`script.rs` 全量错误字符串归纳）：

| code | 类别 | 引擎锚点（原生） | stderr 模式（外部脚本） | 用户举例对应 |
|------|------|-----------------|------------------------|-------------|
| `timeout` | 超时 | `run timed out after {N}s`、script wait failed | `TimeoutError`、`timed out` | 资源无法获取(慢) |
| `resource` | 资源不可得 | `file not found`、`cp: source not found`、`spawn failed`、`launch failed`、`disk`、`No such file` | `FileNotFoundError`、`ConnectionError`、`HTTP 5xx`、`ENOTFOUND`、`ECONNREFUSED` | 资源无法获取 |
| `permission` | 权限 | io::Error `Permission denied`（read/write/rm/mkdir/cp/stat/ls 全套） | `PermissionError`、`EACCES`、`EPERM`、`Operation not permitted` | 文件权限问题 |
| `data` | 数据错误 | UTF-8 解码、`unexpected df output`、非法输出 | `TypeError`、`ValueError`、`JSONDecodeError`、`KeyError`、`IndexError`、`UnicodeDecodeError`、`validation` | 源数据类型错误、数据处理错误 |
| `contract` | 契约违约 | `script not attached`、`missing required param`、`param not in contract`、`invalid script name`、保护根拒绝 | —（引擎层概念） | — |
| `crash` | 崩溃(未知) | 非零退出无模式匹配（兜底） | 其余一切（segfault、OOM-kill、panic） | — |

**判定顺序**（先具体后兜底）：contract → timeout → permission → resource → data → crash。
`ErrorRecord` 同时保留 `raw`（原始 stderr/错误串），分类只是贴标签不丢信息。

```rust
pub struct ErrorRecord {
    pub code: &'static str,      // 六类之一
    pub proc: String,            // 失败 proc
    pub impl_: String,           // 最后尝试的 impl
    pub message: String,         // 截断后的错误消息（≤500 chars）
    pub raw: String,             // 原始 stderr 全文（截断 4KB）
    pub attempts: u32,           // 含 retry 的总尝试次数
}
```

## 3. Either 错误流（executor 语义变更）

### 3.1 错误值化（Left 不再是异常）

proc 全路径失败：**不再中止管线**，`results[p] = Value::Text(§§FIELDS§§err=1§§err_code=timeout§§err_proc=render§§err_impl=ffmpeg§§err_msg=…§§RAW§§stderr)`。

复用 `§§FIELDS§§` 编码的理由：`when.rs::ResultField` 现有解释器直接能读
`@render.err_code`——**零新求值器**，且 api.rs `decode_internal_fields` 自动把错误
字段解码成干净 JSON。

### 3.2 双边语义

- **Right 边（成功流）**：引用 `@p` 的现有 proc。上游 Left 时**默认短路传播**
  （本 proc 自动 Left，error_msg = `propagated from p`）——隐性依赖不被静默跳过，
  fail-closed 传统。`on_left(local)` 可关（见 §5）。
- **Left 边（错误流）**：声明 `.when_err(@p)` 的 proc = 错误处理器。仅当 `p` 已执行
  且为 Left 时 eligible；其 body 可引用 `@p.err_code`/`@p.err_msg` 做精细化分支。

### 3.3 终局判定

- deliver 引用的 proc 链上存在 Left → `ExecResult::Failed { error, partial_results }`
  （**部分结果保留**，api 层输出 `{"ok":false,"error":...,"partial":{...},"err_code":...}`）
- 无错误处理器接住且无 deliver 依赖 Left → 与今天一致的成功语义

## 4. DSL：`.when_err()`（第四种 proc 级修饰）

```
.proc("render")
  .plan(ffmpeg -> run("…"), pillow -> run("…"))

.proc("fallback")                    // 错误处理器：render Left 时才跑
  .when_err(@render)
  .plan(fb -> run("echo using placeholder {topic}"))

.proc("notify_ops")                  // 精细化：只接超时类错误
  .when_err(@render, @render.err_code == "timeout")
  .plan(n -> run("notify 'timeout'"))
```

- 语法：`.when_err(@proc)` 或 `.when_err(@proc, <cond>)`——第二参数复用 when.rs 文法
  （`@p.err_code == "timeout"` 等全部可用）
- 一个 proc 只能有一个 `.when_err`；与 `.when` 互斥（同时声明 = 解析期硬错误）
- **egraph 守卫**：`.when_err` 载体与 when-载体同款，R1/R2/R3 不熔合；L 边进依赖图
  （err_ref 并入 refs），保证被处理者先执行
- `.when_err` 的 proc 自身失败 → 正常 Left 传播（处理器可以失败，可再被别的处理器接）

## 5. 策略引擎（.eval 扩展）

```
# 错误策略行（v0.14）：on error.<code> <action>
on error.timeout    retry(3, backoff=linear)     # 引擎级重试预算（区别于 impl.retry）
on error.resource   retry(1) then escalate
on error.permission escalate                      # 权限问题重试无意义，直接上报
on error.data       reroute                       # 数据错→换路径（排掉当前 impl 再试全 plan）
on error.crash      escalate
on error.*          escalate                      # 兜底：必答策略，缺省 = escalate
```

动作语义：

| action | 行为 |
|--------|------|
| `retry(n[, backoff=linear\|expo])` | proc 级重试预算（跨 impl：一次预算内整 plan 可再来一轮） |
| `reroute` | 排除已失败 impl 后重跑该 proc 剩余路径（impl 级降级的手动加速版） |
| `escalate` | 不再自动处理：Left 落库 + propagate（交给 .when_err 处理器或终局判定） |
| `retry(n) then escalate` | 先重试，预算耗尽后 escalate |

求值顺序：精确 code 匹配 → `error.*` 兜底 → 引擎默认 escalate。策略文件非法
（未知 code/未知 action）= 硬错误（fail-closed，与未知 weight 同款）。

**重试预算与 impl.retry 的分工**：`.retry(n)` 是单 impl 的传输层重试（指数退避，
瞬时抖动）；`on error.X retry(n)` 是 proc 级的错误策略重试（可换 impl，线性退避）。
两层叠加，策略层在外。

## 6. API 面（api.rs）

`run_json` / `run_json_core` 失败输出升级：

```json
{
  "ok": false,
  "error": "All paths failed for proc: render",
  "err_code": "timeout",
  "err_proc": "render",
  "partial": { "search": "...", "gate": "..." },
  "degraded": true
}
```

partial 中的 Left 值解码为 `{"err":1,"err_code":"...","err_msg":"..."}` 干净对象。

## 8. 边界与取舍

- **不破坏 v0.9 兼容**：无 `.when_err`、无策略行的管线行为与今天完全一致（除
  Failed 现在带 partial_results——纯增量字段）
- **错误处理器不熔合、不 CSE**：两个处理器接同一个 Left 是两个语义节点
- **分类是启发式**：`crash` 兜底永不过时——新模式先落 crash，模式库可迭代（纯函数好测）
- **fail-closed 全程**：坏 `.when_err` 条件、未知策略 code/action、缺裁判 = 不放行/硬错
